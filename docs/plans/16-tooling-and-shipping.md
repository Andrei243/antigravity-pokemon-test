# Plan 16 · Tooling and shipping

Written 2026-10-06, before any session.

**Goal**: what turns the repository into something a player downloads and a developer keeps healthy: a licence, a README and a manual with a credits screen behind them; release builds for Windows, macOS and Linux with a version and a changelog; a crash handler, a log file and command-line switches; the screenshot harness running in CI under a software renderer, with nightly runs of what is too slow for every push; live reload of the text data and a developer console; a bot that plays the open game and reports what it could not reach; a content check and a room editor for plan 01 · M11's interiors; performance budgets as tests; the harness in files with an internal facade in place of reflection; the game's state machine without its window; and, last, packs that layer over `Data/` with a manifest and a guide. After those, from the second round of ideas: a cloud session that builds, tests and shoots with local baselines and A/B timing beside it, harness scenarios as text files run by a warm harness, the field's rules drawn as layers in its own view, real play recorded and replayed exactly for bug reports, a soak run that counts what the game holds over an hour, and a first start that measures the machine before it chooses a preset.

## Where we are

- **The front door**: the root holds `CLAUDE.md`, `THIRD-PARTY-NOTICES.md` and the solution. There is no `README.md`, no `LICENSE`, no changelog and no manual. `docs/art/CREDITS.md` lists the fonts and the data sources; nothing in the game shows it. `TitleChoice` is `None, Continue, NewGame, Options, Quit`, and `TitleScreen(SaveData?)` builds its `entries` from it; the style guide's "Opening and title screen" fixes the cards at CONTINUE, NEW GAME, OPTIONS, QUIT. `UiFonts` draws Latin-1 only. Plan 12 · Q15 adds the jukebox to the same menu.
- **The build**: `PokemonPlatinumEngine.csproj` is a plain `net10.0` Exe on Raylib-cs 8.1.0 (raylib 6.0) that copies `Assets`, `Data/**/*.json`, `*.mml` and `scripts/**/*.txt` to the output; no `RuntimeIdentifiers`, no single file, no self-contained publish, no version, no icon, no manifest, nothing that zips a build. `SdfCache.Folder` and `PokemonSprites.CacheFolder` are `cache/models` and `cache/sprites` under `AppContext.BaseDirectory`, so a game under Program Files or inside a read-only `.app` cannot write them. `ModelOverrides.Folders` reads `overrides/models` under the base and the current directory, `CharacterSprites.OverrideFolder` `overrides/sprites`. The save and `settings.json` are written in the working directory; plan 12 · Q1 to Q3 own them (`SavePaths`, a per-user folder, `--portable`, `--save`, a backup and a checksum, `tools/SaveTool`).
- **The program**: `Program.Main` is 53 lines: `GameSettings.Load`, `InitWindow`, `SetTargetFPS(60)`, `--region` through `RegionArgument`, then `Update`/`Draw` until `WindowShouldClose` or `QuitRequested`. There is no exception handler; `GameEngine.cs` has no `catch`; `AudioManager` and `GameSettings` report with `Console.WriteLine`; `Raylib.IsWindowFocused` is called nowhere. `FrameProfiler` (`Enabled`, `Lap`, `Report`) is switched on by the harness's `profile` mode and `FrameTests` alone. `Gl` looks up `glFinish`, `glBindTexture` and `glTexParameteri` and nothing else, so the renderer's name is never read. `GameEngine.Initialize` loads the render texture first and then the databases, `MapDatabase.Initialize`, `LoadScripts`, `CharacterModels.Preload`, `PokemonModels.Preload`, `BattleBall.Preload`, `PokemonSprites.BakeAll` and `SaveManager.LoadGame`, untimed.
- **CI**: `.github/workflows/ci.yml` is one `ubuntu-latest` job: restore, build Release, build `tools/ShotHarness`, `dotnet test`. The harness opens a hidden raylib window (`ConfigFlags.HiddenWindow`), so it never runs there. Its runs repeat (`Dice.Seed`, `FrameClock.Fixed`, and since plan 01 · M7 `GameClock.FixedDate`, because the weather calendar follows the date), and `diff` lists what changed between two folders; it exits 0 whatever it finds. What is too slow for every push has no schedule: `PokemonGeneratorTests.EveryGeneratedModelMeshesSoundly` runs only under `POKEMON_MODELS_ALL=1` (plan 03 · D5), `BattleCoreTests.RandomBattlesAlwaysEndAndLeaveNothingOutOfRange` plays 150 battles where plan 06 · R30 wants thousands, `MusicTests.TestEverySongRendersCleanly` hears the first ten seconds of each song, and `tools/MusicRender`'s clash report is read by hand. Plan 11's risks note that this plan's CI will mesh every rig cold.
- **The harness**: `tools/ShotHarness/Program.cs` is 3,616 lines of top-level statements. `mode` is `args[1]`, `Run(section)` picks the twenty-one sections of `all`, and the modes outside it (`area`, `cities`, `dex`, `versus`, `conditions`, `fieldmoves`, `opening`, `export`, `profile`, `diff`, `contact`, `crop`) are `if` blocks. Its helpers are local functions: `Get` and `Set` on `GameEngine`'s private fields through `BindingFlags.NonPublic` (since plan 02 · S2 `flyScreen`, `poketch`, `poketchView` and `fishing` among them, and `world` and `renderContext` for the renderers), `PastTheOpening`, `Frames`, `Skip`, `Capture`, `Shot`, `ShotCrop`, `At`, `GoTo`, `SetPlayerAnim` (which writes `Player`'s backing fields), `Confirm`, `ToMainMenu`, `Timing`, `Profile`, and `Beside` inside the `story` mode. It calls `StartTransition`, `StartWildBattle`, `HandleStartMenuChoice` and `TryInteract` by name, and reaches the internal classes it needs (`CharacterStudio`, `CharacterSprites`, `PokemonModels`, `PokemonStudio`, `PokemonGenomes`, `PokemonSprites`, `GltfWriter`) through `asm.GetType` and `GetMethod`, because `InternalsVisibleTo` names the test project alone. CLAUDE.md records the rule that none of those methods may take an overload. Since plan 02 · S2 made Surf a script, the `life` mode rides out as the game does (the water faced, `TryInteract` running `common.Water`, Surf's question answered with `engine.Choice`, the Fen Badge lent for it), so `all` runs to its end. Since plan 02 · S4 a new game begins in the player's room with nothing, and every mode but `opening` is first taken past the first chapter (`PastTheOpening`: `StoryMigration.PastTheOpening`, a Turtwig and a few items, in front of the house); `opening` plays the chapter's scenes through the public `GameEngine.StartScript` and `ScriptRunning`. Since plan 01 · M7 the harness fixes the day (`GameClock.FixedDate`, the first of June) beside `Dice.Seed(20261004)` and `FrameClock.Fixed`. `SHOTS_WINDOW`, `SHOTS_4K`, `SHOTS_FILTER`, `SHOTS_TIMING`, `SHOTS_ONLY` and `SHOTS_PRESETS` are its switches; `profile` prints a line of milliseconds a scene and writes nothing.
- **Driving the game**: `GameEngine.Steering` walks the player in place of the keys, `GameEngine.Choice` is the question box, `CoreSetup.PlayerController` lets an `IBattleController` choose for the player's side (`TrainerAi.Instance` is the foe's and a partner's; since plan 06 · R9 it is Platinum's AI, which thinks only for a place with a `Trainer` behind it and draws a move at random for the player's own), `BattleEngine` has `SelectMainMenuOption`, `SelectMove`, `ConfirmMessage`, `IsWaitingForConfirm` and `Result`, `GameEngine.StartScript` and `ScriptRunning` start and watch a script, and `HeadlessScriptHost` plays a script with no screen (`OpeningTests` plays plan 02 · S4's first chapter through it, from the bedroom to the catching lesson). Everything else needs the window: `UpdateOverworld` reads `InputManager` and `player.Update` reads the keys unless `Steering` is set, `Update` reads `KeyboardKey.M`, and `GameEngine` owns `RenderContext`, `WorldRenderer`, `BattleRenderer` and `virtualScreen`. `WorldWalk` (the test project) walks the whole game through its warps on the maps alone.
- **Text data is read once**: `ScriptLibrary.Default` is `shared ??= Load()` over `Data/scripts`; `LoadScripts` makes one `ScriptRunner` with the engine's `FieldHost`; `ScriptRunner.Update` runs `Execute(script.Code[at++])` with nothing watching, and an `Instruction` carries its `Op` and `Line`. `MusicLibrary.Songs` loads under `loadLock` from `MusicLibrary.Directory`. `MapDatabase.Load` reads `Data/maps/*.json` and every world `World.LoadAll` finds. The four databases load in static constructors (`Initialize()` is empty), `TrainerDatabase` reads `trainers.json` the first time a trainer is asked for (plan 06 · R9), `SoundMap` reads `audio/sound-map.json`, all through `GameDataFiles.Directory`, `PathOf` and `Load<T>`. `ModelOverrides.Refresh` is called by tools and tests only. A `ScriptException` ends a script with a notice.
- **Rooms and overlays**: twenty-nine hand-made maps in `Data/maps` (`MapFile`: rows of `TileCodes`, an `InteriorStyle`; plan 02 · S4 added `PlayerHouse2F` and `RivalHouse2F`, plan 01 · M7 the Centers and Marts of the east), written back by `MapFile.FromMap`, which `DataFileTests.TestMapFilesRoundTripWithoutLosingAnything` holds. Eighty-five overlays in `Data/world/sinnoh/overlays` (`WorldOverlayFile`: `BgmTrack`, `Doors` as `OverlayDoor`, `Locked`, `Exits` as `OverlayExit`, which since plan 01 · M7 also carry Iron Island's lifts, since plan 01 · M6 `Through` and `HeldBack`, `Signs` and `SignScripts`, people as `OverlayPerson` with a `MapFile.TrainerRecord`, triggers as `OverlayTrigger` by number), and since plan 01 · M7 the weather calendar (`calendar.json`, `WorldCalendarFile`, read by `MapArea.WeatherOn`) sit over area files (`WorldAreaFile`: `AreaObject` with `Id`, `Looks`, `Trainer`, `HiddenBy` and `Item`; `AreaTrigger` with `Variable` and `Value`; `AreaSign`; `AreaWarp`). The only pictures of either outside the harness are `tools/MapImporter`'s. `PixelGround.Bake(map, margin, buildings)` bakes a room's ground on the CPU, and `Bake(map, window, pad, worldSeeds, out mask)` a chunk's.
- **Measuring**: `FrameProfiler` waits for the graphics card; `FrameTests` hold that the fast bake equals the slow one, never that it stays fast; `WorldRenderer.Streaming` (`StreamingStats`: `Chunks`, `TotalUploadMs`, `WorstFrameMs`, `Waits`) is read by the harness's `world` walk; nothing times `MapScene.Prepare`, `SdfMesher.Mesh`, the static constructors, `World.LoadAll`, `ScriptLibrary.Load`, `Mml.Parse` or a save's round trip.
- **Packs**: nothing layers over `Data/`. `tools/DataImporter/Overrides/items.json` and `species.json` are the patch format already in use ("a name maps to the fields to change; a name the import doesn't have is a new item"). `.gitignore` ignores every `overrides/` folder but the importer's. Plan 05 plans `overrides/audio` (its A4 outcome leaves hand-made cries to it); plan 11 · C1 plans `Data/characters.json` as a file a mod reads.
- **Where sessions run**: CLAUDE.md is written for the Windows machine (a GTX 970, Git Bash, no Python, no `gh`), where the harness's timings mean something. Cloud sessions run in Linux containers (Ubuntu 24.04 with gcc, node, `xvfb-run` and Mesa's llvmpipe, `CLAUDE_CODE_REMOTE` set) with no .NET SDK, so they can neither build, test nor shoot. The repository has no `.claude/`, `.devcontainer/`, `tools/dev/` or `.gitattributes`. CLAUDE.md's recipe for a "before" (`git archive` of a commit into a scratch folder, its harness built there, `cache/` copied from the harness's `bin` folder, the change's files copied over it for the "after") and for timing (before, after, before again) is done by hand each time. `SdfCache.Get` and `PokemonSprites`' bake delete a model's or a sprite's older files as they write a new one, so two trees can't share one cache folder.
- **Input and clocks**: `InputManager`'s four reads (`IsActionPressed`, `IsActionDown`, `Axis`, `GetMovementVector`) read raylib directly; `Program.Main` hands `engine.Update` `GetFrameTime()` capped at 0.1 s. In play `Dice` is unseeded (`Random.Shared`); `GameEngine`'s `fieldRandom` is taken from it as the engine is made, and every map takes its generator from it and every Pokémon its personality as `MapDatabase.Initialize` loads them, before the title. `FrameClock.Now` is `Raylib.GetTime()` unless a tool fixes it; `GameClock.Hour` reads `DateTime.Now` unless the options fix the time of day, and `GameClock.Today` reads `DateTime.Today` unless `GameClock.FixedDate` is set; three more reads of the system clock are `PoketchView.Clock`, the diploma's day in `ModernUi.Pokedex.cs` and `adventureStarted` in `StartNewGame`. Plan 15 · E3 plans `Core/WallClock.cs` as the one reader of real time.
- **What the game holds**: textures, render textures, framebuffers, meshes and shaders are loaded by raw raylib and rlgl calls in sixteen files and freed in twelve; nothing counts them. `PokemonSprites.Baked` only grows (a front and a back of 128 pixels and a 48-pixel icon a species) and `PokemonSprites.Forget` has no caller; `PokemonModels.Trim` and `Release` let models go. `WorldRenderer.Streaming` sums the chunk uploads and waits over a walk, not a frame's; `PokemonSprites.Service` times itself against its 4 ms only.
- **The first start and the presets**: `GameSettings.FirstRun` is true when there was no `settings.json`; `WindowSettings.FitToMonitor` then picks the window (`LargestWindowFor`) and nothing else follows from it. `GameSettings.Quality` is High unless chosen. `RenderContext` is made at the layout's 1920×1080; its scene target is that times the preset's `SceneScale` (2, 1.5, 1) and is opened in three places (`WorldRenderer`, `BattleRenderer`, `TitleScene`), while the half-resolution buffers are 960×540 whatever the preset; `NeedsFxaa` reads the target's width, and `Composite` passes `SceneScale` as the outline width. The title's journey renders the field itself (`WorldRenderer.RenderCinematic` over Twinleaf Town, Route 201 and Sandgem Town), warmed behind `TitlePhase.Notice`. `OptionsScreen.Rows` is every `OptionRow`. The harness's engine reads settings from its out dir (`GameSettings.Load()`), where there are none.
- **Seeing the rules**: the field's rules are seen only in their effect on a shot and in `tools/MapImporter`'s pictures. What they come from is at hand: `Map.IsSolid`, `Map.BehaviourAt`, `Map.HeightAt` beside `Relief.At`, `Map.Triggers` (`StepTrigger`), `Map.Warps`, `Map.AreaAt`, `TileBehaviors.HasEncounters`, `TrainerApproach.CanSee` (a trainer's `TrainerData.SightRange` along its `Facing` until a tile that isn't `IsWalkable`) and `WorldRenderer.ScenesFor`, the three chunks by three round the camera; `WorldRenderer.Straighten` moves what the default shader draws on raised ground.

## Design

**The user's decisions come first.** The licence, the fan-game posture, where releases go and whether a Windows runner is wanted are the user's (below); T1, T2 and T4 wait for them.

**One build, two faces.** A player's build and a developer's are the same executable. The developer's surface (the console, the watcher, the trace) exists only under `--dev` or a new `Developer` setting in `settings.json`; off, the game reads the same files, draws the same pixels and `diff` of `all` is empty.

**One way to drive the engine.** A new internal `Driver` on `GameEngine` (`Core/GameEngine.Driving.cs`) is what every tool uses to place the player, set the state, start a battle or a transition, interact, open a menu and read the game's objects. The harness, the console, the bot and the headless tests go through it, so a renamed field breaks the build instead of a run. It comes before the console and the bot because both are written on it; when T11 splits the state machine out, the `Driver` is a window on that.

**What is written about the game.** A new `Core/Diagnostics/` is GPU-free: a rolling log, a crash report, the start-up phases, a `GameVersion` read from the assembly. The title shows `Major.Minor.Patch` only (the commit goes in the log), so two builds of one version draw the same title and `diff` stays quiet. Nothing leaves the machine.

**CI sees the picture.** Under `xvfb` with Mesa's llvmpipe the harness runs with no card; its pixels differ from the GTX 970's, so a comparison is always between two CI runs: the PR's commit and its merge-base, built side by side as CLAUDE.md's `git archive` recipe does by hand. Determinism is checked outright: one commit run twice must `diff` to nothing.

**Tools that are GPU-free get tests; tools that draw get shots.** The content check, the budgets, the bot's policy, the console's commands, the pack layers and the editor's document are classes the test project drives. The editor's window, the console's overlay and the credits screen are drawn with the kit and shot by the harness.

**Packs layer, never replace.** A new `DataLayers` is a list of roots in load order read by every loader; a later root's file replaces an earlier's, a `*.patch.json` patches a data file by name. A pack-free game is byte-for-byte what it was, and a save records the packs it was played with. Platinum's defaults do not move: a pack changes what the player chose to install, and the save says so.

**Two kinds of machine.** The Windows machine is where milliseconds are read; a cloud session's Linux container, like CI, draws with llvmpipe and reads only counts and pictures from its own kind of machine. Tools are bash scripts or C#, never Python, because the Windows machine has none; the scripts run in Git Bash there. A cloud session, CI and a developer share one recipe for the harness under `xvfb` (T16's `tools/dev/shots.sh`, which T4's `shots` job calls) and one way to share a mesh cache between trees (`POKEMON_CACHE`).

**A look is a file.** A scenario is lines of T6's console plus the harness's own verbs, read by a GPU-free parser the tests drive. Each one begins from a fresh game with the harness's seed, clock and day, so a warm harness draws what a cold one does; what the game holds is written in words beside every picture (`state.json`), so a check reads state as well as pixels.

**A game that repeats, proven.** A recording is the session's seed, the save it began from and each frame's `dt`, actions and wall-clock reading. It plays back only because everything takes its chance from `Dice` and the battle's generator and its time from `FrameClock`, `GameClock` and plan 15 · E3's `WallClock`, which CLAUDE.md already requires; T19 makes the whole game prove it, not only the harness's shots. Recording begins in `Program.Main`, never inside `GameEngine`, so the harness and the tests, which make engines of their own, are never recorded, and the live game keeps real time: the clock is read once a frame and written down. Only what decides play is hashed, never what is drawn, so a chunk or a sprite baked later on a slower machine doesn't part a replay.

**Measured, not assumed.** The first start times the title's own field scenes and picks the preset that fits the style guide's budget; dynamic resolution moves the picture, so it is a row of the options, off unless chosen, and the style guide's "Quality presets" names it first. The chooser and the scale's controller are GPU-free and tested on fed timings; the harness keeps both off, so its runs repeat.

**What the game holds, counted.** Every GPU resource goes through one thin wrapper that keeps a ledger by owner, and a soak run comes back to the same state lap after lap: a count higher on the return is a leak, and a frame that misses its sixtieth of a second is given a cause.

### T4 · CI: the harness under a software renderer, the matrix and the nightlies
- `ci.yml`: NuGet cached; `--logger trx` and a step that lists the ten slowest tests; a `shots` job on ubuntu with `xvfb` and `mesa` (`LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`), the harness's `cache/models` restored by `actions/cache` keyed by a hash of the model and mesher sources. The job runs `field`, `menus`, `battle` and `story` on the PR's commit and on its merge-base (a second checkout, built apart), `diff`s them, uploads the PNGs and the boards as artifacts, and fails when shots moved unless the PR carries the label `shots-change`; it also runs `field` twice on the same commit and fails when that `diff` is not empty. Timings are not read: llvmpipe's milliseconds mean nothing.
- A `windows-latest` build-and-test job if the user wants one (decision 4); `macos-latest` in the nightly.
- `nightly.yml` on a schedule: `POKEMON_MODELS_ALL=1`; `BATTLE_FUZZ=5000` read by `RandomBattlesAlwaysEndAndLeaveNothingOutOfRange` (its default stays today's count); `tools/MusicRender` over every song, `--sounds`, `--ambience` and `--cries --all`, failing on its clash report (a new exit code: today it returns 1 only on a bad command line); `tools/MapImporter` against `Sources.DecompCommit` with its `.cache` restored and `report.md` uploaded; the harness's `all` and `dex`; T7's bot and T10's strict budgets once they exist. CONTRIBUTING.md names the required checks the user sets on `main`.
- Tests: none of the engine's; the workflow is its own check.
- **Done when** a PR that moves a drawn pixel shows its boards in the Actions summary and must say so, and a night meshes the whole dex, fuzzes thousands of battles, renders every song and imports Sinnoh.

## Risks

- **llvmpipe at 4K is slow.** The virtual screen is 3840×2160 whatever the window; four modes may take the better part of an hour on a shared runner. If so, PRs keep build and test, the shots go nightly, and the determinism run stays on every push with `SHOTS_FILTER` narrowing it.
- **Shots never cross machines.** A CI board compared with a local run shows the renderer, not the change.
- **The split moves 3,000 lines.** T5 and T11 change no pixel on purpose, and `diff` of `all` is the proof at every step; a `BattleEngine` whose constructor asks `AudioManager` for its cries needs it to stand in headless, which `Listen` already does for what is played.
- **Dev mode reads the repository.** A release build never finds a solution above it and reads its own `Data`; a test holds that `DevMode` is off without the switch.
- **The crash save must never replace the real one**, and the report must hold no path with the user's name in it.
- **The bot can loop.** It is time-boxed, seeded and re-plans on `Revision`; a goal that fails three times is dropped and reported.
- **Budgets on shared runners are noisy.** Medians, headroom and a monthly trend, with strict numbers only on the nightly's own runner.
- **A pack changes play.** The save records it, the Platinum preset stays what it was, and the sample pack is ours; the gitignore rule for `overrides/` holds.

## Decisions for the user

1. **The licence for the code.** *Recommended:* MIT, with the fan-game notice beside it in the README (non-commercial, no affiliation, the trademarks as `THIRD-PARTY-NOTICES.md` says). Alternative: GPL-3.0, which keeps forks open, or no licence, which lets nobody redistribute.
2. **The fan-game posture.** *Recommended:* the title's notice and the README say it plainly and give a contact for takedown; no donations and no store. Alternative: no statement beyond the notice.
3. **Where releases go and what the files are called.** *Recommended:* GitHub Releases of this repository, zips named after the project and the version (`v0.y.z` until the story is complete). Alternative: a separate site, which someone has to keep.
4. **A Windows runner.** *Recommended:* yes, build and test on `windows-latest` on every push; it is the development platform and the minutes are free for a public repository. Alternative: Windows in the nightly only.
5. **Ship the mesh cache.** *Recommended:* yes, tens of megabytes for a first start of seconds. Alternative: bake at first start behind a line on the notice.
6. **An update check.** *Recommended:* none; the title shows the version and plan 07's server tells an out-of-date client. Alternative: an opt-in row that reads the releases feed.
7. **The developer's surface in a player's build.** *Recommended:* compiled in and off without `--dev`, so there is one build. Alternative: a build configuration of its own.
8. **The editor.** *Recommended:* T8's check first, T9 only when plan 01 · M11 begins. Alternative: rooms stay text edited by hand with the check and the plan pictures.
9. **Packs.** *Recommended:* T14 after T11 settles the loaders, T15 when someone wants to make one. Alternative: keep the three `overrides/` folders and no packs.
